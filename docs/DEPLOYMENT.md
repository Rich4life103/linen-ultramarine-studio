# Deployment

The app is split across two hosts because Vercel runs **serverless functions with no
persistent disk**, while this backend needs a writable filesystem for its SQLite database
and uploaded media.

```
┌──────────────────────┐        fetch (cookies, CORS)        ┌───────────────────────────┐
│  Frontend — Vercel   │ ──────────────────────────────────► │  API — Render web service │
│  React + Vite (static)│ ◄────────────────────────────────── │  Express + SQLite + uploads│
└──────────────────────┘                                     └───────────────────────────┘
```

- **Frontend → Vercel**: static SPA build (`client/dist`), served from the edge.
- **API → Render**: long-running Node service with a writable disk for `studio.db` and `/uploads`.

Only two variables tie them together:

| Host | Variable | Value |
| --- | --- | --- |
| Vercel | `VITE_API_URL` | The Render service URL, e.g. `https://linen-ultramarine-api.onrender.com` |
| Render | `CORS_ORIGIN` | The Vercel site URL, e.g. `https://linen-ultramarine.vercel.app` |

### Redeploying

- **Frontend**: `cd client && vercel --prod`
- **API**: push to `main`, then trigger a deploy — either from the Render dashboard
  (*Manual Deploy → Deploy latest commit*) or via the API:
  `POST https://api.render.com/v1/services/<serviceId>/deploys`

> **Auto-deploy note**: the service was created through the API with
> `autoDeployTrigger: commit`, but push-triggered webhooks additionally require the Render
> GitHub App to be installed on the repository. Install it from
> <https://github.com/apps/render/installations/new> (or Render Dashboard → *Connect GitHub*)
> to get deploys on every push. Until then, trigger deploys manually as above.

## 2. Deploy the API to Render

A Blueprint (`render.yaml`) is included.

1. Sign in at <https://render.com> (GitHub sign-in is fastest).
2. **New → Blueprint** → pick this repository.
3. When prompted, set **`CORS_ORIGIN`** to your Vercel URL (you can add it after step 3 and
   redeploy — it is read at boot).
4. Render builds `server/` and starts `npm start`. Confirm `https://<service>.onrender.com/api/health`
   returns `{"ok":true,...}`.

The first boot creates and seeds the database automatically
(`elena@elenavance.design` / `studio2024`).

### Persistence on the free tier

Render's **free** instance type does not support attached disks, so on free the database is
re-created and re-seeded whenever the service restarts (it spins down after inactivity). The
app is fully functional; it just resets to the seeded state. For real persistence:

- Switch `plan: free` → `plan: starter` (paid, ~$7/mo) and uncomment the `disk:` block plus
  the `DATA_DIR`/`UPLOAD_DIR` variables in `render.yaml`.

The code already reads both directories from the environment (`server/src/paths.js`), so this
is a configuration change only.

## 3. Deploy the frontend to Vercel

A `client/vercel.json` is included (SPA rewrites so client-side routes work on refresh).

1. Sign in at <https://vercel.com>.
2. **Add New → Project** → import this repository.
3. Set **Root Directory** to `client`. Vercel detects Vite automatically.
4. Add environment variable **`VITE_API_URL`** = your Render URL (no trailing slash).
5. **Deploy**, then copy the resulting `https://<project>.vercel.app` URL.
6. Go back to Render, set `CORS_ORIGIN` to that URL, and redeploy.

> Preview deployments are allowed automatically: the API also accepts any
> `*.vercel.app` origin, so branch previews work without extra config.

## CLI alternative

```powershell
npm i -g vercel
cd client
vercel --prod            # prompts to link/create the project
vercel env add VITE_API_URL production
```

## Production notes

- **Cookies**: the session cookie is `httpOnly`, and in production it is `SameSite=None; Secure`
  because the frontend and API live on different domains. Both must therefore be HTTPS
  (Vercel and Render both are).
  - **Known limitation**: because the API is a *different site* from the frontend, browsers that
    block third-party cookies (Safari, Firefox by default, or Chrome with "Block third-party
    cookies" enabled) will not persist the studio session on those browsers. The public
    portfolio is unaffected. To make the studio work everywhere, proxy the API through the
    frontend's own origin instead: add a `/api/:path*` rewrite in `client/vercel.json` pointing
    at the Render URL, leave `VITE_API_URL` unset, and the cookie becomes first-party.
- **Persistence**: on Render's free instance type the SQLite file lives on an ephemeral
  filesystem, so the database re-seeds on every restart or deploy. See
  [Persistence on the free tier](#persistence-on-the-free-tier) for the paid-disk upgrade.
- **Secrets**: `JWT_SECRET` is generated by Render automatically; rotate it by editing the env
  var. Rotating signs everyone out.
- **Changing the admin password**: there is no self-service flow; edit the seeded user or
  re-seed after clearing the database.
